# Separately authorized staging validation proposal

**Inference:** local checks support a conditional go for a bounded synthetic verification exercise of the implemented private-only patch. This proposal is not permission to contact services. It does not authorize deployment, migration, schema edits, real participant data, performance/load testing or CODEX 2.

## Required separate authorization

**Inference:** approve a named nonproduction Supabase project and Vercel staging deployment, operator/actor, exact release artifact, synthetic fixture namespace, allowed fixture creation/role/override changes, browser/API/RLS/Storage reads and cleanup. Confirm allowed authentication method without exposing secrets in logs. Specify whether creating eight synthetic Auth identities is authorized. Authorize only a tiny synthetic asset and the activity caps below. No production host/project, migration or durable-sharing activation is in scope.

**Requires live verification:** positive project identification, deployed schema/grants/row-limit/exact-count support and synthetic-only fixture inventory. If these cannot be proved, stop before scenarios. A successful staging gate needs a dated run record with actual request/byte counts and unresolved outcomes; mocks are not that record.

## Fixtures and budgets

**Inference:** use eight synthetic authenticated actors: respondent, assigned facilitator, same-cohort participant, unrelated participant, exact Hub leader, Course Creator, Admin, Super Admin; plus anonymous. Create three synthetic Hubs (open, approval-required, invite-only), two synthetic courses/versions, two concurrent cohorts on one canonical course journey and one subgroup. Limit to six generic responses and one LMU synthetic assessment with ten section records. Use nonsense answers and non-sensitive authored content; no copied participant text or published production curriculum. Record every fixture ID and ownership before testing. Do not create durable-sharing tables or counterfeit consent grants.

**Inference:** projected 60 sequential scenarios at 5–8 backend requests each plus up to 100 setup/cleanup requests: **400–580 expected Supabase requests**. Count metadata queries carry exact-count overhead; actual server cost/latency is unknown. Hard stop at **1,000 total Supabase requests**, **25 MiB total transfer**, **100 mutation requests**, **8 synthetic Auth users**, **500 synthetic rows**, **1 uploaded object ≤512 KiB**, or **60 minutes**, whichever occurs first. Count Auth, REST/RPC, signing/download, failed/retried calls and cleanup. No Realtime subscription, polling, load/concurrency benchmark or unbounded retries. Allow only scoped reads with a maximum 50 returned fixture rows per verification query.

**Inference:** request/egress counters must be observable in an authorized browser network log/proxy or project metrics before beginning. If counts cannot be measured, do not start. Reserve 100 requests/20 mutations for cleanup; stop new scenarios at 900 requests/80 mutations. Larger-than-expected fan-out, unknown project, real rows, privacy disclosure, uncertain receipts or cap approach triggers stop. Clean up only recorded fixture IDs; never bulk-delete by a partial name. If budget cannot complete cleanup, retain the manifest for a later separately approved cleanup.

## Stop/go, cleanup and rollback

**Inference:** any unauthorized read/export, contact leakage in progress, cross-identity write, missing acknowledged save, false success, unexpected global creator authority, silently truncated authorization, failed essential operational workflow or cap breach stops the exercise. Keep redacted evidence/fixture IDs; inspect authoritative state before retry. Fix locally and reauthorize continuation if needed. Do not spend budget on a load test to diagnose correctness.

**Inference:** a passed limited gate establishes only the tested private-only patch. It does not approve creator/scoped reporting/sharing activation, small-group analytics or closed-Hub discoverability changes. Production remains separately gated on sign-off and accepted deferred-feature scope. Use reviewed safe code for rollback, preserve privacy guards, revoke only fixture grants within authorization, and clean up only manifest IDs. Application rollback cannot recall downloads, issued URLs or committed/in-flight writes/publication. Any corrective production data/grant operation requires a new concrete approval.
